# 志愿云志愿时长批量录入助手

把名单（文本或 Excel）转成**可直接粘贴到志愿云后台的录入模板**。

**线上直接用（无需安装）：**

👉 **https://qiu-free.github.io/zhiyuanyun-hour/**

> 网页是**纯前端**的：所有计算都在你自己的浏览器里完成。
> **没有任何服务器** —— 你输入的姓名和身份证号不会离开你的电脑，
> 我们看不到，也不会有日志。打开页面就能用。

**也可以在自己电脑上跑：**

| 方式 | 命令 | 说明 |
|---|---|---|
| 🌐 网站 | `npm run web` → 打开 http://127.0.0.1:5180 | 图形界面，能实时校验、直接改错、看排期 |
| ⌨️ 命令行 | `npm run text -- --file 名单.txt --clip` | 适合脚本化、批量处理 |

> **本工具不联网、不登录志愿云、不代替你提交。**
> 它只生成文本，由你自己到后台粘贴——你始终能看到将要提交的内容。

> **设计取舍**：本项目**刻意不做自动提交**。
> 原因见 [为什么不做自动提交](docs/为什么不做自动提交.md)：
> 你看不到自动提交的内容，而这个场景里「能核对」比「省事」重要。

## 一、先读这一节：三条硬性业务规则

这三条决定了工具为什么这么设计，也是「一次性全部录完」不可行的原因。

### 1. 单次录入上限 50 小时

系统限制一次最多给一个志愿者录 50 小时。

**超过 50 小时不是不能录，是要分多次录**（同一人可以累计，没有总额上限）。
两种办法：

**A. 原地分批**（在同一项目里分几次）：

| 总时长 | 怎么分 | 录完约需 |
|---|---|---|
| 50 小时 | 一次录完 | — |
| 51 小时 | 50 + 1 | 5 天后 |
| 80 小时 | 50 + 30 | 5 天后 |
| 120 小时 | 50 + 50 + 20 | 10 天后 |

**B. 换项目分流**（分到不同项目，大幅提速）：

因为时间锁是「同一人在同一项目」的限制，**不同项目互不等待**。
两种办法可以**同时用** —— 工具会算最优组合。

以 120 小时的人为例：

| 有几个项目 | 怎么安排 | 完成时间 |
|---|---|---|
| 1 个 | 50 → 等5天 → 50 → 等5天 → 20 | 10 天 |
| 2 个 | 项目1录50 + 项目2录50（当天），等5天后再录20 | **5 天** |
| 3 个 | 项目1录50 + 项目2录50 + 项目3录20 | **当天** |

规律：**每 50 小时需要一个项目**才能当天录完。

> ### ⚠️ 注意：「当天录完」≠「一次粘贴」
>
> 50 小时是**每人每次**的硬限制，跟项目多少**无关**。
> 项目多只让这些提交**都在同一天做完**，不能把 120 小时变成一次提交。
>
> | 总时长 | 最少提交次数 |
> |---|---|
> | ≤ 50 小时 | 1 次 |
> | 51 ~ 100 小时 | 2 次 |
> | 101 ~ 150 小时 | 3 次 |
> | 151 ~ 200 小时 | 4 次 |
>
> 即 `ceil(总时长 ÷ 50)`。面板上会写清每人要提交几次。

> ⚠️ 代价：志愿者的记录会分散在多条里、项目属性可能影响时长归集。
> 工具会把利弊都列出来，也支持手填"我实际有几个项目"。

> **项目不够时不会硬塞**：按项目数均分会得到超 50 的值
> （120h 分 2 个 → 60+60，粘进去必然失败）。
> 所以用**贪心排期**：当天优先填满各项目，剩下的排到解锁之后。

工具自动算出方案，并按轮次/分组给出各自的粘贴文本
（`/api/batches` 与 `/api/multi-project`）。

> 早期版本把 >50 当成数据错误并丢掉时长的数值，用户既看不到总数、
> 也不知道要分两次录。现在改成「需分批」状态，数值保留，可用可导出。

### 2. 录入后有强制时间锁（最关键）

同一志愿者在同一项目中，**首次录入时长越长，下次可录入的等待时间越长**：

| 首次录入时长 | 距下次录入需等待 |
|---|---|
| ≤ 10 小时 | 24 小时 |
| 10 ~ 20 小时 | 48 小时 |
| 20 ~ 30 小时 | 72 小时 |
| 30 ~ 40 小时 | 96 小时 |
| 40 ~ 50 小时 | 120 小时 |

**注意**：时间锁只约束**同一个人在同一项目**。不同人之间互不影响，
所以第 1 轮可以把「一次就能录完的人」和「超限人的第一批」放在同一天录。

**影响**：如果有人要录 80 小时，你至少要分两批、跨 1~5 天完成，无法一次跑完。

### 3. 表格里必须有「身份证号」，学号系统不认

官方补录模板的必填列是：

```
序号 | 姓名* | 身份证号码* | 荣誉时数值*（单位：小时） | 补录原因*
```

注意：**没有学号列**。系统靠「姓名 + 身份证号」定位志愿者。

- 学号 → 只对你们学院内部核对/发补助有意义，工具会保留并做交叉校验，但**不会提交给系统**。
- 身份证号 → **必须准确**，错一位就匹配不到人，或者匹配到同名的人。

> 如果表格里只有姓名没有身份证号，工具无法可靠工作：重名会录错人。

## 二、快速开始

### 环境要求

- Windows / macOS / Linux 均可
- Node.js ≥ 20（本项目在 Node 24 下开发验证）
- 一个能进志愿云项目后台、能录时长的**项目管理员**账号

### 安装

```bash
git clone https://github.com/qiu-free/zhiyuanyun-hour.git
cd zhiyuanyun-hour

npm install
```

用 pnpm 的话：

```bash
pnpm install --node-linker=hoisted
```

> `--node-linker=hoisted` 建议加上。pnpm 默认的符号链接布局在部分环境下
> 会导致模块解析失败。项目根目录的 `.npmrc` 里已经配好了，通常不用手动带。

> **依赖只有 3 个**：`xlsx`（读表格）、`dotenv`（读配置）、`node-forge`
> （登录模块用到的加密，当前主路线其实用不到）。
> **没有浏览器依赖**——本工具不驱动浏览器。

### 准备表格

把你的 Excel/CSV 放到 `data/` 目录（该目录已被 gitignore，不会上传），
列名支持中文或英文：

| 姓名 | 学号 | 身份证号 | 志愿时长 | 备注 |
|---|---|---|---|---|
| 张三 | 20230101 | 110101200501011239 | 8 | 2025年迎新志愿服务 |
| 李四 | 20230102 | 130102200503152342 | 12.5 | 社区清扫 |

也支持英文表头：`name` / `studentId` / `idCard` / `hours` / `remark`

> 表格上方有标题行、说明行没关系，程序会自动找真正的表头。

### 第一步：校验数据（必做）

```bash
npm run validate -- --file data/volunteers.xlsx
```

会检查身份证校验位、出生日期、时长格式、单次 50 小时上限、
重复人员、同名不同证件、姓名异常等，并生成 `output/*-report.md`。

**报告里有 ❌ 就不要往下走。**

### 第二步：生成可粘贴文本

```bash
npm run paste -- --file data/volunteers.xlsx --clip
```

生成格式（每人一行，英文逗号分隔）：

```
姓名,身份证号,时长,备注
张三,110101200501011239,8,2025年迎新志愿服务
李四,130102200503152342,12.5,社区环境卫生清扫
```

`--clip` 会直接放进剪贴板。然后：

1. 打开志愿云后台 → 我的项目 → 项目的「记时」/「批量录入」
2. 在文本框里 `Ctrl+V`
3. 确认导入

产物：
- `output/*-paste.txt` —— 要粘贴的文本
- `output/*-核对表.md` —— 含学号，供学院内部核对人数和时长

### ⚠️ 关于分隔符的坑（重要）

如果用英文逗号分隔，**备注里不能再出现英文逗号**。

比如备注写成 `迎新,社区清扫`，后台会把这一行切成 5 段，
导致时长被当成备注、备注被吃进下一列，**录到错的人身上**。

工具会拦下这种行并明确报错：

```
❌ 有 3 行无法生成（会破坏列结构）：
  第3行 李四
      • 备注中含英文逗号：迎新,社区清扫
        建议：把逗号换成顿号「、」或分号「;」
```

处理办法：

```bash
# 办法一：回表格把逗号改成「、」，重新运行
# 办法二：让工具自动替换（会改动备注内容）
npm run paste -- --file data/volunteers.xlsx --fix --clip
```

被拦下时退出码为 `3`，不会伪装成成功。

### 🚩 缺失信息一律报备，程序不代填

**这是本工具的硬性规则：缺什么就报什么，绝不猜。**

「补录原因」是系统必填项，且会写进志愿者档案。如果表格里没有「备注」列
（或某行备注为空），程序会停下来，列出缺哪些人，并告诉你要向发起人确认什么：

```
🚩 有 9 行缺少「补录原因」，需要向发起人报备：

  行号      姓名          学号            时长
  ──────────────────────────────────────────────
  第2行     张三          2025213817    8
  第3行     李四          2024213884    8
  ...

  ✅ 请向发起人确认：
     • 本次补录的原因 / 活动名称是什么？
     • 是否所有人员用同一个原因？还是因人而异？
```

此时**退出码为 `4`**，且**不会复制到剪贴板**（避免你粘贴到残缺数据）。

拿到答复后二选一：

```bash
# 1) 回表格加一列「备注」逐人填写
# 2) 所有人原因相同时，用参数指定
npm run paste -- --file data/volunteers.xlsx --reason "已确认的原因" --clip
```

> `.env` 的 `ZY_DEFAULT_REASON` 也**默认为空**，就是为此。
> 只有在你已向发起人确认、且所有人用同一原因时才填它。

### 可选：排期（有人时长超 50 小时时）

```bash
npm run schedule -- --file data/volunteers.xlsx
```

## 四、时间锁调度（多人多批场景）

如果本批数据里有人要录的时长超过 50 小时，工具会自动给出排期建议。

```bash
npm run schedule -- --file data/volunteers.xlsx
```

**一个反直觉但很重要的结论**：不要「小步快跑」，而应该**每批尽量大**。

因为「完成耗时」只统计批次之间的等待（最后一批录完不再等待）：

| 总时长 | 每批 ≤10h | 每批尽量大 | 快的是 |
|---|---|---|---|
| 12h | 2 批 / 等 24h | **1 批 / 等 0h** | 每批尽量大 |
| 45h | 5 批 / 等 96h | **1 批 / 等 0h** | 每批尽量大 |
| 120h | 12 批 / 等 264h | **3 批 / 等 240h** | 每批尽量大 |

所以只要单次不超 50 小时，就一次录完——**等待时间为 0**。
工具默认即采用这个策略（`--strategy few`）。

若某人不希望单批时长过大，可切换：`--strategy fast`（每批 ≤10h，但批次多）。

> 以上数据由 `node scripts/selftest-schedule.js` 实测得出，可自行复现。

## 五、安全与合规

**必须读完再用。**

1. **用你自己的账号，用你自己的权限。** 本工具没有任何破解、绕过验证码、伪造身份的功能。它模拟的就是你在后台点鼠标的操作。

2. **身份证号是敏感个人信息。** 按《个人信息保护法》，批量处理需具备合法性基础（通常是志愿者本人知情同意）。请：
   - 数据文件不要放网盘、不要发微信群
   - 用完后删除 `data/` 下的原始表格
   - 不要把 `data/`、`output/` 提交到 Git（`.gitignore` 已排除）

3. **录入内容必须真实。** 虚报志愿服务时长属于弄虚作假，涉及评奖评优的会构成违规。工具只是提高效率，**不能用来编造时长**。

4. **控制速度。** 默认慢速运行（每次操作间隔若干秒），避免给服务器造成压力。不要改成高并发。

5. **平台改版会导致失效。** 本工具依赖页面结构和接口，平台升级后需相应调整。

## 八、网站是怎么跑起来的

### 纯前端，没有服务端

```
浏览器
  ├── index.html
  ├── web/app.js        界面逻辑
  ├── web/localApi.js   四个接口的本地实现
  ├── core/*.js         业务逻辑（与 CLI 共用同一份）
  └── vendor/xlsx.mjs   读写 Excel
```

**为什么这样设计**：这个工具处理的身份证号是高度敏感的个人信息。
如果做成传统的「浏览器 → 服务器」，使用者的数据就要发到服务器上，
随之而来的是存储、日志、泄露风险，以及合规义务。

纯前端方案下：

- 数据只在使用者的浏览器内存里
- 关掉页面就没了
- 没有服务器要维护，也不用备案
- 托管在 GitHub Pages 上，免费

`core/pipeline.js` 是**服务器与浏览器共用的唯一真相来源**。
`server/api.js` 只是给它包了一层 HTTP（供 CLI 和测试使用），
所以线上和线下的计算结果完全一致 —— 这一点有 34 项自检专门盯着。

### 构建与部署

`.github/workflows/deploy-pages.yml` 会在每次推送到 `main` 时：

1. 安装依赖
2. 跑自检（**不通过就不会部署**）
3. `node scripts/build-site.js` 构建 `dist/`
4. 发布到 GitHub Pages

本地想验证产物：

```bash
npm run site           # 构建
npm run site:preview   # 预览（这是线上跑的那一份）
```

构建脚本会自检两件事，避免「本地能跑、线上不能用」：

- `index.html` 引用的每个文件是否都存在
- `core/` 里有没有模块依赖 `node:` 内置模块（浏览器加载会直接报错）

### 目录布局必须两边一致

线上部署在子路径下（`/zhiyuanyun-hour/`），所以：

- 所有路径用相对写法（`./web/app.js`），**不能写 `/app.js`**
- `core/` 的模块写的是 `import XLSX from 'xlsx'`（裸模块名），
  浏览器不认识，靠 `index.html` 里的 importmap 映射到 `./vendor/xlsx.mjs`

本地服务（`npm run web`）刻意提供**完全相同的布局**，
这样不会出现「本地好使、线上 404」。

### 一个已知问题：xlsx 的版本

Excel 读写用的是 `xlsx@0.18.5`。这个版本有两个已知 CVE
（原型污染、ReDoS，均在解析恶意文件时触发）。

**为什么风险低**：纯前端运行，只处理使用者自己选的文件，
不会影响服务器或他人；最坏情况是自己的浏览器标签页卡住。

**如果想彻底解决**：SheetJS 官方已不在 npm 发布新版本，
需要改用他们自建的 CDN 版本，或者换成 `exceljs` 之类的替代品。
本项目暂未更换，因为这会牵动读取/写入的全部逻辑。

## 九、部署到 GitHub

### 会上传什么

**44 个文件、约 370 KB**，只有源码、文档和测试：

```
src/          源码（core / cli / server / web）
scripts/      自检与工具脚本
docs/         文档
package.json  pnpm-lock.yaml  README.md
.gitignore    .npmrc  .env.example
```

### 不会上传什么（已被 .gitignore 排除）

| 路径 | 内容 | 原因 |
|---|---|---|
| `data/` | 你放名单的地方 | **真实姓名+身份证号** |
| `output/` | 生成的结果 | 含真实数据 |
| `.env` | 本地配置 | 可能含补录原因 |
| `privacy-blacklist.local.json` | 真实名单的哈希 | 见下 |
| `node_modules/` | 依赖 | 别人 `npm install` 即可 |
| `dist/` | 网站构建产物 | 由 GitHub Actions 自动生成 |
| `.playwright/` | 浏览器 | 本项目已不用浏览器 |

### 关于 `privacy-blacklist.local.json`

`scripts/check-privacy.js` 用它检测项目里是否残留真实个人信息。
它**只存 SHA-256 哈希**，但中文姓名空间有限、哈希可被暴力破解，
所以这个文件**不放进仓库**——仓库只保留检查机制。

**别人克隆后**没有这个文件也能跑，只是不做「已知名单」比对，
结构性检查（15~20 位可疑号码）照常生效。

**你自己换电脑时**，把这个文件一起带过去（或者重新生成）即可。

### 别人克隆后怎么用

**只想用网站**：直接打开 https://qiu-free.github.io/zhiyuanyun-hour/
（或者把这个链接发给别人，不用装任何东西）

**想在本地跑**：

```bash
git clone https://github.com/qiu-free/zhiyuanyun-hour.git
cd zhiyuanyun-hour
npm install
npm run web
# 打开 http://127.0.0.1:5180
```

`npm test` 可以跑全部自检，确认环境正常。

### 启用 GitHub Pages（只需做一次）

推上去之后，去仓库页面：

**Settings → Pages → Build and deployment → Source 选「GitHub Actions」**

选好后，每次推送到 `main` 都会自动构建并发布。
Actions 标签页能看到进度，绿勾表示部署成功。

线上地址是：`https://<用户名>.github.io/<仓库名>/`

> 注意：**Source 必须选「GitHub Actions」**，不要选「Deploy from a branch」——
> 后者会去读仓库根目录，而网站产物在 `dist/` 里且由 Actions 生成。

### 如果你想 fork 后自己维护

推之前务必执行 `git status`，确认清单里没有这四项：
`data/`、`output/`、`.env`、`privacy-blacklist.local.json`。
